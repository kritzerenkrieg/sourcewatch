# Decisions

Working list for deciding features, approach and technical details. This file overrules `ARCHITECTURE.md` and `ROADMAP.md` wherever they disagree.

Each item has a code: the letter is the `ROADMAP.md` phase, the number is its sequence within that phase. Codes are stable and never reused.

Status:
- **Decided**: settled and binding. State the choice and the reason in a few words.
- **Inspect**: needs a look first (spike, library, benchmark, test). Research only.
- **TBD**: read, but not discussed yet. Ask, don't guess.
- **Question**: raised (usually by the agent) and not yet read by the human. Triage it by moving it to TBD, Inspect or Decided. Treat it like TBD until then.

A phase starts only when its rows are Decided.

| A1 | Language and runtime | Decided | Go, self-hosted, single binary. Stack as listed in `ARCHITECTURE.md`. |
| A2 | Secrets | Decided | Tokens and webhook URLs live in env vars or a `600` config file, never in the repo. |
| A3 | Where it runs | Decided | Debian server. |
| A4 | Unprompted DMs from user-installed apps | Decided | No. DMs are opt-in only, so no test is needed. |
| A5 | `discordgo` viability | Decided | `discordgo` v0.29.0 for the bot (slash commands, DMs, webhook edits, 50007 all present; rate limits handled in the REST layer). Release cadence is slow but nothing needed is missing. |
| A6 | Config file format and module path | Decided | Config is a `600` JSON file named by `SOURCEWATCH_CONFIG`, with `SOURCEWATCH_DISCORD_TOKEN` and `SOURCEWATCH_WEBHOOK_URL` env overrides (standard library only). Go module path is `github.com/kritzerenkrieg/sourcewatch`. |
| A7 | Project name | Decided | The project is called sourcewatch (it was pawnz). The settings use `SOURCEWATCH_*` environment variables, and the old `PAWNZ_*` names are still read. With no database configured, `sourcewatch.db` is used, or an existing `pawnz.db` when that is all there is, so an install from before the rename keeps its data. |
| B1 | Data source | Decided | A2S directly, not the Steam master server or an aggregator. The one exception is the GameTracker fallback in B5. |
| B2 | A2S client | Decided | Use `rumblefrog/go-a2s` v1.0.3. We wrap it for the 2 s timeout, 2 retries and `context` cancellation, since it has none of those. Replaced by our own client (B8). |
| B3 | Polling values | Decided | 60 s interval with ±5 s jitter. |
| B4 | Player identity source | Decided | A2S names for now. Steam linking and the SourceMod plugin stay in G1. |
| B5 | Fallback to GameTracker when A2S fails | Decided | Approved. B1 stays the rule (A2S directly); GameTracker is a fallback only. Behavior: (a) only when A2S has failed the offline threshold (3 cycles) for a server; if GameTracker says the server is alive, report it online with the data from there and mark it as via GameTracker; (b) fetch each page at most once every 5 minutes per server, with a User-Agent that names sourcewatch, and apply it only when the page's own "Last scanned" time moved forward; (c) use status, name, map, player count and the player table (names). Because the page can be minutes old, a player who joins and leaves between two scans is missed, `playercount` and `map` notifications can arrive late, and data older than 20 minutes is treated as unavailable (the server stays offline); (d) `/status` says when data came from GameTracker and how old it is; (e) when the page cannot be parsed or the fetch fails, the server stays offline, never guessed. Risks: the page is HTML, not an API, so a layout change breaks the parser (a saved copy of the page becomes a test fixture); I have not read their terms of use. Their robots.txt allows generic crawlers. A page without `Status: Alive` (no Status field, or any other value) means the server is offline. |
| B6 | Retries for a server already offline | Decided | Keep 3 tries for every query (B2), also for a server that is already offline. At this scale the cost is small, and a server that comes back is seen within a minute. |
| B7 | Servers that stay down | Decided | Keep polling every minute (B3) for as long as someone listens, however long the server has been down, so its return is announced within a minute. |
| B8 | Own A2S client | Decided | go-a2s answers only one challenge. `css.nide.gg` sometimes sends a new challenge in reply to the first one, several times in a row, and go-a2s then failed with "Unsupported protocol header", for every game server on that IP at once. sourcewatch now has its own small A2S client, in the standard library only, that keeps answering challenges on the same socket, up to 5 per query, and joins split replies (Source format, uncompressed). It reads A2S_INFO up to the bot count and the names from A2S_PLAYER. The 2 s timeout, the retries and `context` stay as in B2, and go-a2s is no longer a dependency. |
| C1 | Subscription conditions | Decided | The command is `/notify`. A notification is built from these conditions: `map` (map name), `player` (username), `playercount` (integer), `status` (boolean, online/offline) and `title-query` (matches the server name, not case-sensitive, and finds the text even when wrapped, e.g. `EVENT` finds `[event]servername`). Replaces `/subscribe` in the older docs. |
| C2 | Cooldown and "full" values | Decided | Cooldown is 5 seconds. There is no separate "full" threshold: filling up is expressed with `playercount`. |
| C3 | Data retention | Decided | Keep history, accumulative and efficient. `/notify` can query the existing records. |
| C4 | `/notify` conditions | Decided | Each `/notify` subcommand makes one notification with one condition: `map`, `player`, `playercount`, `status` or `title-query`. The `id` option adds the condition to a notification you already have, so it has several and all of them have to hold together (up to 8). It fires once when they all become true, and waits until they stop being true. For `playercount` the `value` holds the comparison and the number: `>=10`, `>10`, `<=10`, `<10`, `=10` or `!=10`. A plain number such as `10` means at least 10 (the same as `>=10`), and the number can be 0 to 64. There is no separate operator option. `title-query` checks whether the server name contains the text. `player` matches the A2S name, with an optional Steam ID parameter as hardening (see C7). The details of combining are E13. |
| C5 | History storage | Decided | Store history only when something changes, so polls do not flood the database. Track maps, players (as sessions: name, server, first seen, last seen) and server titles by change, and status. |
| C6 | Where `/notify` is used | Decided | Server bot first. A Discord server sets its target game servers (E9), and the players in that Discord server use `/notify` against it. Who sets the target and how is E3. Personal DM notifications are lower priority and TBD (E4). |
| C7 | Playercount trigger, suggestions, Steam ID | Decided | (a) `playercount` fires once when its condition becomes true, then rearms when the condition stops being true. (b) Every notification, of any type, has a cooldown of 60 minutes after it fires, unless an admin changed the default of the Discord server (E15) or it was changed with `/notify settings` (in minutes). The cooldown is counted per notification ID (per game server for a notification for all servers). (c) When a `player` or `map` value has no exact match in history, the bot suggests similar names for the user to pick. (d) The optional Steam ID parameter on `player` is on hold until G1. |
| C8 | History retention | Decided | Keep history forever, no pruning. Estimated at about 50-60 MB a year per busy 60-slot server, mostly player sessions. |
| C9 | Events held back by the 5 s per-user cooldown | Decided | An event held back by the per-user cooldown (C2) is not saved as fired: the notification stays as it was, so it fires at the next poll of that server if its conditions still hold. Nothing is lost, and a user still gets at most one message every 5 s. |
| D1 | Webhooks or bot | Decided | The bot posts to channels, not webhooks. There is no webhook provider. The bot does not send or refresh a message to a channel every minute: it listens, and sends only when something happens. |
| D2 | Mentions | Decided | Mentions use the Discord user ID (`<@id>`), never a name. `allowed_mentions` is always set with `parse` empty and only that one user ID listed, so nothing else can ping. Player names from A2S are shown as plain text and cannot ping. |
| D3 | Status board | Decided | No standing board message. `/status`, with no options, shows every game server watched in that place when someone asks: name, online/offline, players of max, map, last updated, and who is online. Its reply is public, so everyone in the channel sees it. It is one of two public replies, with `/notify show`; all others stay private to whoever ran the command. Players on the Discord server's blacklist (E15) are left out of the list. |
| D4 | Channel delivery that Discord refuses | Decided | When Discord refuses a channel notification because the channel is gone or the bot may not see it or post in it (errors 10003, 50001 and 50013), it is handled like a refused DM (E7): the notification is marked undeliverable, nothing is posted anywhere else, and the user is told the next time they use `/notify`, with the reason and what to do. For a message that mentions several people (E16), that is each of them. |
| E1 | Gateway or HTTP interactions | Decided | Gateway bot: outbound WebSocket, so no public endpoint is needed on a self-hosted machine. |
| E2 | Notification channel and consent | Decided | Discord only. DMs are opt-in; running `/notify` is the consent (E8). |
| E3 | Adding game servers | Decided | A game server is added with `/server add` and an address. Who may run it and how many a Discord server can have are in E9. The command shape is E10. |
| E4 | `/server` in a DM with the bot | Decided | In a DM with the bot, a user can add several game servers with `/server add`, and `/server remove` stops listening to one. Notifications there come by DM. The bot polls a server only while someone listens to it. |
| E5 | List and help commands | Decided | `/notify list` lists the user's notifications. `/help` lists all commands. |
| E6 | Delivery of a player's notification | Decided | A new notification is delivered in the channel where it was made, mentioning only that player by ID (D2), or by DM when it was made in a DM with the bot. Delivery is changed afterwards with `/notify settings` (E14). |
| E7 | DM delivery when Discord refuses the DM | Decided | When a player picks `dm`, the bot sends a test DM at once and, if Discord refuses it (error `50007`), tells the player in the reply to message the bot first. A later refusal marks the notification undeliverable, and the bot tells the player the next time they use `/notify`. Nothing is posted in the channel. |
| E8 | Command naming | Decided | The commands are top-level slash commands with no shared prefix: `/server`, `/notify`, `/status`, `/admin` and `/help`. `/notify` has subcommands: `map`, `player`, `playercount`, `status`, `title-query`, `list`, `show`, `remove`, `settings` and `reset`. `/server` has `add` and `remove`, and `/admin` has `settings`. (Discord does not allow a dot, so `/sourcewatch.server` was not possible.) `/notify remove` deletes one notification by ID, `/notify settings` changes one, `/notify reset` deletes all of yours here, `/notify list` shows yours to you, and `/notify show` shows them to everyone in the channel. Running `/notify` is the consent for DMs (replaces `/subscribe` in E2). Other bots in the same Discord server may use the same names, such as `/help` or `/status`; Discord shows which app each belongs to. |
| E9 | Who sets a target, and how many | Decided | Manage Server is the permission needed to run `/server add` and `/server remove` in a Discord server. More than one game server can be a target. When no `server` is given, a command applies to all of them: `/notify` makes one notification for each game server (each with its own ID), and `/status players` lists the players of each. Naming a `server` limits it to that one.
| E10 | Shape of `/server` | Decided | Two subcommands, each with a required `address`: `/server add` and `/server remove`. Removing suggests the servers you watch. (This replaces the earlier single `/server` with an `action` choice. Discord only rejected `server` being both a subcommand and a group for `remove`, and two plain subcommands avoid that.) |
| E11 | Shape of `/notify` | Decided | `/notify` has one subcommand per type: `map` (option `map-name`), `player` (option `username`), `playercount`, `status` (`online` or `offline`) and `title-query` (option `value`). Each also takes the optional `id` and `server`. Delivery and cooldown are not options of these: a new notification uses the defaults (E15), and `/notify settings` changes them. There are also `list`, `show` (the same list, shown to everyone in the channel), `remove` (by ID), `settings` (E14) and `reset` (no options). After saving, the reply says "Notification saved as ID: <id>". The list writes each notification as, for example, `(via channel, cooldown 60 mins)`. |
| E12 | Limits and default cooldowns | Decided | (a) A Discord server, or a user in a DM with the bot, can watch at most 3 game servers. (b) Every notification of every type stays quiet for 60 minutes after it fires by default, counted per notification ID (C7). Not discussed, so left as built: at most 25 notifications per user, and addresses that resolve to private or loopback IPs are refused. |
| E13 | How combined notifications behave | Decided | (a) All conditions of a notification have to hold (AND), at most 8, except that several `map` conditions are ORed (E21). (b) It fires once when they all become true together, and again only after at least one stopped being true and they all hold again. The cooldown is per notification ID. (c) Every type is a condition that is true or false right now: the map is X, the player is online, the player count compares, the server is up or down, the name contains the text. A single condition fires when it becomes true. (d) A new notification, or one you add a condition to, does not fire for conditions that already hold. It waits for them to stop holding and become true again. (e) is E14. (f) `/notify remove` asks for an ID and deletes that notification. `/notify reset`, with no options, deletes all of your notifications in that place, after asking with buttons. |
| E14 | Settings of a combined notification | Decided | The game server, the place it is delivered to (channel or DM) and the cooldown belong to the whole notification, not to one condition. `id` adds a condition and keeps them, so `server` together with `id` is refused. Delivery and cooldown are not options of the type commands at all, so they are changed only with `/notify settings`. `/notify settings` takes an `id` and changes `cooldown` (minutes), `active` (`enabled` or `disabled`) and `delivery` (`channel` or `dm`). The `id` is optional. It is a notification's number, or `all` for every notification the user has in that place, and without it the settings are for all of them. With no setting given, a number shows that notification's settings, and all shows how many are enabled and disabled. The game server cannot be changed. A disabled notification does not fire. Enabling it starts it over, so it does not fire for conditions that already hold. Changing the delivery to `dm` sends a test DM first, once even for `all` (E7). Changing it to `channel` uses the channel the command is run in, and is not possible in a DM with the bot. |
| E15 | `/admin settings` | Decided | Admins (Manage Server) set, for their own Discord server only: (1) `channel-delivery` enabled or disabled, enabled by default: when disabled notifications go by DM and `/notify settings` refuses `channel`. (2) `default-delivery`, `channel` or `dm`, the default being `channel`: how a new notification is delivered. (3) `default-cooldown` in minutes: the cooldown of a new notification. (4) `active`, enabled by default: when disabled, sourcewatch does nothing in that Discord server, no notifications are sent and every command except `/admin` says so, and a DM with the bot is not affected. (5) A blacklist of player names: `blacklist-add` and `blacklist-remove`. Settings 2 and 3 apply to notifications made afterwards. Without options `/admin settings` shows the current settings. Details of the blacklist are E17. |
| E16 | Notifying people together | Decided | When people have the same notification in the same channel and it fires at once, one message mentions all of them, like "@Kritz @Player2 @Player3 …", instead of one message each. Only people with the same message in the same channel are grouped. DMs are always one person each, a person is mentioned once, and a message mentions at most 40 people (a bigger group is sent as several messages). |
| E17 | Blacklist details | Decided | Confirmed as built. (a) A name is matched exactly, not case-sensitive, and the blacklist is per Discord server. (b) Nobody in that Discord server can make a `player` notification for it, alone or added to another notification with `id`. (c) Existing notifications that track it stop firing, without being deleted. (d) `/status` leaves the name out of the player list, and shows "(hidden)" when every name is left out. The player count still counts them. (e) It does not hide the player on other Discord servers, and does not stop the bot from storing their name in its history (C5). A player cannot ask for a global opt-out; only the people running the bot can do that. |
| E18 | Notification IDs | Decided | Each person numbers their own notifications, separately in each Discord server and in DMs: their first is 1, then 2, and so on, so they can organize their own list. A new notification takes the lowest number that person has free there, so the number of a deleted notification is used again, and `/notify reset` makes their numbering start at 1 again. Another person's numbers never get in the way. Inside the bot each notification also has an ID unique across everybody, which nobody sees. Existing notifications were numbered once, per person and place, in the order they were made. (Corrected: the first version shared one numbering across everybody, which the user had not chosen.) |
| E19 | Notifications that come back after being skipped | Decided | A notification starts over when it comes back after being skipped, like enabling a disabled notification (E14): when an admin turns sourcewatch back on in a Discord server (E15), and when a refused delivery is switched back on after the user was told (E7, D4). It then waits for its conditions to become true again, so it never fires hours late. |
| E20 | `id` you do not have | Decided | When `/notify <type>` is given an `id` that the user has no notification under in that place, a new notification is made with that number instead of an error, and the reply says so. An `id` of one of the user's own notifications still adds the condition (E13), and `server` is allowed in the new case. Since numbers are per person (E18), another person's notifications never block a number. |
| E21 | AND and OR inside a notification | Decided | (a) Several `player` conditions in one notification are always ANDed: every one of those players must be online. (b) Several `map` conditions are always ORed: the server being on any of those maps is enough. (c) Between the types it stays AND, so `{map a OR map b} AND {player 1 AND player 2}` fires only when the server is on a or b and both players are online. (d) The other types (`playercount`, `status`, `title-query`) stay plain AND, and are not mentioned in the help text. (e) Moving from one of the maps to another one keeps the notification true, so it does not fire again until it stopped being true (E13b). (f) Messages and lists show the maps as one part, "the map is one of `a`, `b`", joined to the other parts with "and". (g) The `map` and `player` command descriptions and the README say so. |
| E22 | `/admin settings gametracker` | Decided | `/admin settings gametracker:enabled\|disabled`, enabled by default, for that Discord server only. When disabled, the game servers it watches keep being tried with the normal direct query (B1) and are never looked up on GameTracker (B5), so they are declared offline after the usual failed tries. It is the same switch, off, as B5's fallback for that Discord server. |
| E23 | GameTracker setting when places share a game server | Question | Built as follows, because a game server is polled once however many places watch it. Confirm or change. (a) The fallback is used for a game server as long as at least one place that watches it has it enabled, and a DM always has it enabled. A game server only in the config file also keeps it. (b) A Discord server that turned it off ignores data that came from GameTracker: its notifications are not checked against it and nothing changes for them, and its `/status` shows "no direct answer" for such a server instead of the data. (c) Direct answers count everywhere as usual. |
